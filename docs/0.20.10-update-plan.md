# 0.20.10: verified phone-app updates

## Goal

Upgrade the existing Android installed app from 0.20.8 to 0.20.10 through the phone-driven update flow, without clearing storage, reinstalling, or pairing either computer again. Do not declare the operation complete until the required phone build is actually running and the selected relays have reached their targets.

This is an implementation plan, not a claim that the handset failure has been fixed.

## Established evidence

- Both relays updated to 0.20.9. Fedora recorded successful hosted-app deployment before restarting its relay.
- The phone displays running version 0.20.8 and reports that 0.20.9 is deployed to its origin and ready to load.
- Manual Load Update, force-stopping, and clearing browser cache did not recover the user's installed app. Do not repeat these as the proposed fix.
- Tested public HTML, redirect chains, and decoded JavaScript responses are consistent with 0.20.9, including mobile user agents and compressed/uncompressed requests. This does not establish what the handset received.
- The false completion is reproduced with the released 0.20.8 bundle: after a new document navigation, two simulated 0.20.9 relays produce “2 of 2” and “100%” while the phone code remains 0.20.8. The experiment deliberately served old assets; it proves the accounting defect, not the handset's asset-delivery cause.
- Hermes in the launch dropdown is supplied by the relay and is not evidence of a new frontend bundle.

## Required invariants

1. Published metadata, delivered assets, and the running app are separate states. Metadata availability is not installation success.
2. A phone update is an explicit plan item, independent of which relay owns deployment.
3. Success requires the running phone's verified build identity, not merely a successful navigation request or reconnect.
4. Every release entry references one consistent, integrity-checked asset set.
5. Recovery stays on the existing origin and preserves the PWA identity, device credentials, relay configuration, preferences, and update progress.
6. Automatic recovery is bounded. Exhaustion produces an actionable failure, never a reload loop or false success.

## Implementation sequence

### 1. Capture the failing Android delivery path

Inspect the actual installed-app context through Android/Chromium remote debugging. Fedora currently lacks `adb`; arranging that tooling and an authorized handset connection is a prerequisite for this step.

Capture a single manual update attempt:

- Host browser/provider and installed-app context.
- Initial and final document paths, navigation commits, and redirects.
- Requested script URL, delivered script digest, and running version/build identity.
- Whether responses came from memory, disk, a service worker, or the network.
- Relevant cache headers, CDN edge identifier, and navigation/script exceptions.

Compare those requests with the verified release files and the actual Cloudflare custom-domain cache/redirect configuration. Diagnose an origin mismatch, stale response, navigation failure, or provider-specific behavior from evidence; do not assume ordinary browser caching. Exclude relay credentials, invitation fragments, tokens, and conversation content from diagnostic output.

**Exit condition:** identify where the handset diverges from the intended release and retain a reproduction or handset trace. The status-accounting fix below can proceed independently, but the release cannot be signed off without resolving this delivery failure.

### 2. Fix phone-update accounting

Primary files:

- `frontend/src/lib/updates.ts`
- `frontend/src/lib/types.ts`
- `frontend/src/components/SettingsView.svelte`
- `frontend/src/components/UpdateProgressDialog.svelte`
- `frontend/src/App.svelte`

Separate a `phoneAppRequired` flag and expected phone identity from the existing deployment-owner field, `appRelayId`. Manual Load Update must persist a phone item even when both relays are already current or no deployment owner is involved. Normalize existing session-stored plans into the new contract without losing progress.

Completion becomes:

```text
all selected relays at their required versions
AND
(phone update not requested OR required phone build actually running)
```

Preserve existing handling of compatible newer releases. Explicit relay-only operations may report that the selected relays are ready, but must not claim to have updated the phone.

For the reported case, show two completed relays plus an incomplete phone item, not “2 of 2 / 100%.” Distinguish publishing, downloading/loading, loaded, and failed-to-load states. A reload-attempt marker is not a success acknowledgement.

### 3. Make bundle cutover verifiable

Primary files:

- `frontend/vite.config.ts`
- `frontend/src/lib/updates.ts` and `frontend/src/lib/config.ts`
- `frontend/src/App.svelte`
- `frontend/public/_headers`
- `internal/web/handler.go`
- Frontend compression, size, validation, and release scripts

Use a build-specific entry pathname and content-addressed asset filenames rather than relying only on query parameters attached to stable filenames. Generate one release descriptor tying version/assets identity, entry URL, and JS/CSS digests to the actual shipped bytes. Use browser integrity checks for the entry's executable/style resources.

Keep `/` and `/index.html` as stable bootstrap contracts. Give their responses and redirects explicit non-storing cache policy; only genuinely content-addressed resources may be immutable. Implement equivalent routing for Cloudflare Pages and relay-hosted apps. Update the Go asset allowlist and every build/compression/size validator to consume the new layout; do not leave two competing asset schemes.

Require acknowledgement from the newly initialized app before clearing the pending phone target. Use the existing update state/storage infrastructure for bounded retries and failure reporting. At most two automatic attempts per target/session; subsequent recovery must be explicit. A deadline or integrity failure must explain which stage failed and expose only nonsecret diagnostic identity.

The Android trace from step 1 determines any additional platform/deployment correction. Content-addressed delivery is not, by itself, proof that the observed failure is resolved.

### 4. Recover already-stuck 0.20.8 clients

This is part of the fix, not an optional follow-up. Changes inside 0.20.10 JavaScript cannot help a client that never loads that JavaScript.

Make the existing 0.20.8 navigation contract, `/index.html?herdr_reload=...`, reach the new build-specific entry through deployment-side/bootstrap routing. Verify actual Pages redirects, query handling, same-origin behavior, and installed-app launch behavior rather than relying on the local static server alone.

Provide a same-origin build-specific recovery entry for diagnosis, but do not make opening a special URL or reinstalling the app the normal update procedure. Preserve manifest `id`, `scope`, and `start_url` so the change does not create a second installed app or new storage origin.

**Exit condition:** the already-installed 0.20.8 app reaches and runs 0.20.10 through its existing phone update controls, retaining both pairings.

### 5. Verify delivered assets before deployment success

Primary files:

- `internal/appdeploy/worker.go` and its tests
- `internal/release/` where the release descriptor is verified
- `scripts/package-release.sh`
- `scripts/stamp-web-version.mjs`
- `frontend/scripts/validate-build.mjs`
- Release workflow and packaged-release checks

Public verification must check the entry document and referenced asset digests, not only `version.json`. Follow only permitted same-origin redirects, use bounded reads/timeouts, and reject missing assets, stale entries, mixed builds, or incorrect decoded representations. Exercise the compressed delivery paths as well as identity responses.

Retain existing local manifest/web-hash verification and Brotli equality checks. Packaging must reject a frontend built for another product version instead of relabeling its metadata as the requested release. Validate the running version of the packaged frontend in the release browser check.

The old relay's updater will not execute new 0.20.10 verifier code during the first upgrade. Therefore the release/deployment pipeline must also run the strengthened public checks for the first 0.20.10 deployment. Do not rely solely on future relay updates to close this gap.

### 6. Regression and release gates

Extend existing update/component/browser/deployment suites with behavioral regressions:

| Scenario | Required result |
| --- | --- |
| Both relays current, phone still old after manual reload | Phone remains an incomplete item; never reports total success |
| Updated metadata but stale HTML or JS | Detect/recover within the bounded policy, or report failed-to-load |
| Navigation commits but old bundle initializes | No success acknowledgement; pending phone target survives |
| Missing/mixed/corrupt asset or incorrect compressed representation | Deployment or loading fails explicitly |
| Successful new-bundle initialization | Phone item completes only after target identity is observed |
| App backgrounded/restarted during cutover | Progress resumes without loops, duplicate relay installs, or credential loss |
| Same-version asset update | Distinct build identity loads and is acknowledged |
| Explicit relay-only update | Accurate relay-only completion; no claim about updating the phone |

Use two real bundles and a deterministic local origin that can switch or fault responses. Existing tests that only observe a cache-busted URL or persisted field are insufficient; assert the running app's identity and consumer-visible completion state.

After integration, regenerate the committed web bundle, run `make check`, and require all release/CI checks to pass. Then verify the packaged candidate through both relay-hosted delivery and the actual Pages deployment path.

**Mandatory handset gate:** on the affected Android installed app, complete 0.20.8 → 0.20.10 with Fedora and MacBook connected. Confirm About shows 0.20.10, progress includes the phone, reopening remains on 0.20.10, and both credentials/preferences survive. Also cover a normal 0.20.9 → 0.20.10 upgrade. Desktop emulation or a fresh browser tab does not satisfy this gate.

### 7. Publish 0.20.10

Update the release version, asset metadata, generated web bundle, `CHANGELOG.md`, and `docs/updates.md` together. Document verified behavior and failure recovery, not unproven cache-clearing advice. Preserve the existing relay rollback and transport compatibility guarantees.

Do not publish 0.20.10 as fixing this incident if only the false-success dialog is corrected. The loaded-phone version and affected-handset gates are required.

## Scope limits

No transport/authentication redesign, origin migration, pairing reset, service-worker app-cache framework, or dependency additions without a demonstrated need. No unrelated Hermes changes. Handset diagnostics are for identifying and verifying this failure, not a new telemetry system.
