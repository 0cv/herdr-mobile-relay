# DR-1: Independently bound Tailscale Serve session authority

**Status:** R1-A source/design review draft. The design is not independently accepted and no owner decision has been recorded. `ownerApproved=false`, `runtimeQualified=false`, `featureReady=false`; R2 implementation has not started. Production `ServeRouteOwned=false` remains unchanged.

## Decision requested

Keep Tailscale Serve unavailable until one implementation can prove, in-process and for an owner-selected distribution, that this relay run owns one exact foreground session, can observe that session's liveness, and can retire only that session. Do not derive authority from a matching route, PID, route-set difference, health result, or a session ID read from daemon state.

**Preferred candidate for owner review, not selected:** a version-pinned Tailscale LocalAPI client owned by the long-running relay process. That same process would acquire managed owner **O**, hold the LocalAPI watcher and opaque session handle, own the local server/control lifecycle, and conditionally install the route. The existing separate `tailscale serve` foreground child must not be treated as authority. Keep `ServeRouteOwned=false` production behavior unchanged unless a separately approved R2 change completes this protocol.

The recommendation is conditional on explicit owner choices for the exact Tailscale macOS distribution(s), Linux package/build scope, Go dependency, local write-privilege model, and version policy. Source research does not qualify all Linux or Mac installations.

## Scope and evidence boundary

The existing adapter is pinned to Tailscale **1.102.4**, upstream commit `bbcd7d1fc2054b9189ebc1531acf74bd880ca0c8` (tag `v1.102.4`) in [`CONTRACT.md`](CONTRACT.md). Its read-only `Inspect` has no independently supplied session authority and deliberately leaves `ServeRouteOwned=false` ([`tailscale.go`](tailscale.go), [`contract.go`](contract.go)). The launcher gates pairing, QR output, reprint, monitoring, and owned cleanup on positive ownership. That refusal is correct and must remain.

This R1 slice fetched and hashed pinned public source files; it did not download, install, build, or execute a Tailscale artifact, contact a daemon/control plane, or run any Tailscale activity. Source-backed behavior is not runtime qualification, signature verification, or proof that a particular distribution's installed client and daemon match the source. The complete citation, immutable URL, line range, SHA-256 and source/inference distinction are in the JSON inventory.

## Source observations and implications

### Foreground sessions are real but process-local

- Pinned `tailscale serve` foreground mode calls `WatchIPNBus`, takes the non-empty `SessionID` from the first initial notification, places its nested config under `ServeConfig.Foreground[sessionID]`, submits the config, then blocks on that watcher. Its HTTPS path calls `enableFeatureInteractive` before that flow. See pinned [`serve_v2.go`](https://github.com/tailscale/tailscale/blob/bbcd7d1fc2054b9189ebc1531acf74bd880ca0c8/cmd/tailscale/cli/serve_v2.go#L435-L557).
- The daemon generates a 16-byte random hexadecimal watcher ID, records it with the active notification watch, and on **any handler exit**—orderly close, request cancellation, EOF/error, or involuntary watch loss—runs `DeleteForegroundSession(sessionID)`. That deletion unconditionally removes whatever value then occupies that one foreground key; it does not compare the nested route or wait for the client to observe the exit. Distinct session keys and other Serve fields are untouched. A changed/replaced value under this same ephemeral key may therefore be erased before the relay can react to an involuntary loss; same-key preservation on that path is outside this candidate's guarantee. On profile/config reload, inactive foreground sessions are filtered. These are upstream lifecycle behaviors, not evidence that this relay's current parent owns another process's watcher; no finite cleanup deadline is promised. See [`ipnlocal/local.go`](https://github.com/tailscale/tailscale/blob/bbcd7d1fc2054b9189ebc1531acf74bd880ca0c8/ipn/ipnlocal/local.go#L3717-L3880) and [`ipnlocal/serve.go`](https://github.com/tailscale/tailscale/blob/bbcd7d1fc2054b9189ebc1531acf74bd880ca0c8/ipn/ipnlocal/serve.go#L422-L438).
- `client/local.WatchIPNBus` documents that its API is not stable. It decodes a long-lived response with an unbounded `json.Decoder`; a future relay adapter must impose the repository's byte, depth, duplicate-key and cancellation bounds rather than inheriting an unbounded trust boundary. See [`client/local/local.go`](https://github.com/tailscale/tailscale/blob/bbcd7d1fc2054b9189ebc1531acf74bd880ca0c8/client/local/local.go#L1482-L1547).
- **There is no source-backed atomic guard that the supplied foreground ID is still an active watcher when `SetServeConfig` is applied.** `validateServeConfigUpdate` checks Serve/listener conflicts, not watcher membership ([`ipnlocal/serve.go`](https://github.com/tailscale/tailscale/blob/bbcd7d1fc2054b9189ebc1531acf74bd880ca0c8/ipn/ipnlocal/serve.go#L1736-L1834)). `WatchNotificationsAs` registers its watcher-map-removal defer before the later `DeleteForegroundSession` defer, so LIFO exit runs the session deletion first and removes the watcher map entry afterward ([`ipnlocal/local.go`](https://github.com/tailscale/tailscale/blob/bbcd7d1fc2054b9189ebc1531acf74bd880ca0c8/ipn/ipnlocal/local.go#L3845-L3880)). The two steps acquire/release the backend mutex separately. A `SetServeConfig` can therefore interleave after a no-op session deletion but before map removal; its subsequent config reload can still see the watcher ID as active, and map removal does not itself run another Serve cleanup ([`ipnlocal/serve.go`](https://github.com/tailscale/tailscale/blob/bbcd7d1fc2054b9189ebc1531acf74bd880ca0c8/ipn/ipnlocal/serve.go#L328-L398), [`ipnlocal/serve.go`](https://github.com/tailscale/tailscale/blob/bbcd7d1fc2054b9189ebc1531acf74bd880ca0c8/ipn/ipnlocal/serve.go#L1571-L1650)). This is a source-derived race, not a runtime hypothesis.

**Implication:** the relay must create and retain the watcher itself, but a held watcher plus ETag is not an atomic session-admission primitive. The R2 design must distinguish a settled write from an unresolved one; a read that finds no key cannot settle a POST that may still reach `SetServeConfig`. An in-memory, non-serializable owner handle pairs the watcher connection with the initial session ID. The ID is not a bearer secret or independent authority; never accept it from an environment variable, session file, route inspection, or caller. PID/process-group supervision remains useful for lifetime management but cannot replace this handle.

### Conditional Serve mutation is necessary and has limits

- `GET /localapi/v0/serve-config` returns the configuration and ETag. `POST` passes `If-Match`; the daemon compares it with a hash of the current config and validates/applies the update under its mutex. A stale non-empty tag returns HTTP 412. **An empty/missing tag disables the optimistic concurrency check and permits overwrite.** `client/local.SetServeConfig` can send an empty tag if its caller supplies one. See [`client/local/serve.go`](https://github.com/tailscale/tailscale/blob/bbcd7d1fc2054b9189ebc1531acf74bd880ca0c8/client/local/serve.go#L17-L56), [`ipn/localapi/serve.go`](https://github.com/tailscale/tailscale/blob/bbcd7d1fc2054b9189ebc1531acf74bd880ca0c8/ipn/localapi/serve.go#L25-L78), and [`ipnlocal/serve.go`](https://github.com/tailscale/tailscale/blob/bbcd7d1fc2054b9189ebc1531acf74bd880ca0c8/ipn/ipnlocal/serve.go#L306-L398).
- A correct non-empty ETag makes the compare-and-update atomic against conditional/concurrent config changes. It does not prevent a separately authorized writer from deliberately omitting `If-Match`. For initial route registration, the chosen design rejects an absent ETag and stale 412, and never replays registration after an ambiguous acknowledgement; it switches to the separate read/compensate/verify path below. Cleanup may issue a new conditional compensation only after a fresh read proves the same exact owned route is still present.
- The local state store is written. Foreground scope makes the route ephemeral to the watcher lifecycle; it is not a tailnet control-plane mutation. The relay must not set DNS, prefs, Funnel, or Serve HTTPS capabilities, and must not use `SetServeConfig(nil)` or a global reset for cleanup.

**Implication:** initially require a fully validated empty Serve config and no existing exposure, obtain a live watcher/session, then register exactly the intended single foreground route with its non-empty ETag. A missing ETag, unsupported state, conflict, timeout, or ambiguous acknowledgement is a refusal—not permission to create/adopt a route.

### Identity, HTTPS, version, and local authorization are independent checks

- Pinned `ipnstate.Status` exposes daemon `Version`, `Self.ID`, `Self.UserID`, `Self.DNSName`, and `CurrentTailnet` name/MagicDNS data. It does not supply a tailnet/account UUID in those fields. The current repository contract's typed identity requirements remain the baseline; revalidate the full available tuple before mutation, readiness, reprint, and arm.
- The CLI source checks the node's HTTPS capability and may enter `enableFeatureInteractive` for HTTPS Serve. R2 must not silently copy that interactive feature-enablement step. Require HTTPS capability already present, matching node/tailnet/DNS identity, and successful public TLS/health readiness; `CertDomains` alone is not proof. If the capability is absent, stop and ask the user to enable it through the normal Tailscale UI/CLI and retry.
- The existing read-only `tailscale version --json --daemon` path reports client metadata and daemon `Status.Version` separately; `client/local` also sees a `Tailscale-Version` response header but only offers a *notification callback* for a mismatch, not an unconditional admission gate. R2 must preserve an exact client/daemon/build-policy check; status or a short version alone is insufficient. The API methods and watcher are explicitly unstable between Tailscale releases. See pinned [`version.go`](https://github.com/tailscale/tailscale/blob/bbcd7d1fc2054b9189ebc1531acf74bd880ca0c8/cmd/tailscale/cli/version.go#L21-L81) and [`client/local/local.go`](https://github.com/tailscale/tailscale/blob/bbcd7d1fc2054b9189ebc1531acf74bd880ca0c8/client/local/local.go#L164-L175).
- `client/local` and `safesocket` source show Linux/Unix socket defaults, Darwin's standalone socket fallback, and sandboxed macOS localhost/token transports. Darwin non-GUI clients can source a same-user proof token from the App Store extension's open file (`lsof`) or MacSys shared file; the client adds it as HTTP Basic auth. The source also documents explicit-token permissions for sandboxed clients. However, the exact installed macOS product/channel and its server/auth integration are not identified or exercised here. Linux socket path, daemon build features, socket permissions, operator UID and sudo rule are distribution-specific too. Therefore neither “Linux works” nor “Mac works” is an R1 qualification.

## Required R2 state machine (design only; do not implement in R1)

1. **Disabled / prepare (read-only).** Use bounded LocalAPI requests and the existing strict version/identity/Serve inspection policy. Reject unknown Serve fields, background or Funnel state, existing/extra routes, unsupported OS/build/version, missing write authorization, missing HTTPS capability, inconsistent node/tailnet/DNS/version, or any API/parser error. No route write, feature-enablement flow, pairing arm, or link.
2. **Consent.** Obtain explicit per-run consent before the first route mutation. Explain that the daemon writes local Serve state and will expose one HTTPS proxy route while this foreground run is alive. No `--yes`/reprint shortcut may create consent or authority.
3. **Revalidate.** After consent, repeat identity, exact version and complete Serve checks; require a non-empty ETag and the exact supported empty state. Do not infer absence from a missing query/default value.
4. **Acquire O and prepare unarmed local service.** In the managed `runServe` process, acquire **O** before managed resources and use a proposed Tailscale-only `deviceauth.OpenDeferred` read-only store path. Before route readiness it must not create/protect/chmod the device-auth directory or initialize/rewrite `devices.json`; it may only validate/read existing state without mutation. Keep all E2EE resolver delegation closed until owner/route readiness so no authentication completion can write the store early. Start local listeners and private localcontrol in a locally healthy, owner-held but pairing-unarmed state, with route mutation and **L** acquisition disarmed. Report `owner_held/local_ready` only from the in-process owner. The shell may persist the selected transport/origin and non-secret run record only after receiving that status. The constructor currently calls `armBootstrap` eagerly; R2 must add the Tailscale-managed deferred-open/arm policy and preserve existing non-Tailscale behavior.
5. **Activate and conditionally register.** Only an authenticated localcontrol `activate` after the shell persistence step opens **L** in this same process; require an initial notification with non-empty session ID and keep `(watcher, sessionID, version, identity)` in one opaque in-memory handle. Do not pass it through shell arguments, files, or localcontrol caller parameters. Re-read Serve config/ETag and submit exactly one POST for only `Foreground[sessionID]` with the exact HTTPS/host/port/`Proxy /`/loopback-backend tuple. Require a non-empty ETag; disable automatic POST retries. Record a tri-state result: `settled-success` only after the complete validated success response from the synchronous endpoint, `settled-no-write` only after a complete source-backed refusal such as ETag 412, otherwise `unresolved` (timeout, cancellation, reset, truncated/malformed reply, or unknown error after submission). A watcher-loss signal cancels readiness; the daemon has no active-session check. An unresolved POST is not readiness and cannot be retired by an absent GET alone.
6. **Actual readiness, then arm.** While the watcher remains live, independently verify the same node/tailnet/DNS/version tuple, exact complete Serve route under this session, no unsupported/extra/Funnel state, local listener/inventory readiness, and expected HTTPS certificate/health. Separate local HTTP health from managed pairing readiness: `/healthz` may prove the already-bound local backend, but `localcontrol.Ready`/pairing status remains false until the in-process authority check succeeds and bootstrap arm is durably acknowledged. Only then print a QR/link. The arm callback revalidates the live handle itself; caller-supplied `owned=true` or session ID is not accepted.
7. **Monitor/reprint.** Monitor watcher completion/errors, repeated identity/version reads, exact Serve config, listener state and public health. Any mismatch revokes pairing and stops the public listener. If a changed same-key value is detected while L remains live, make no cleanup write and do not intentionally cancel L; quarantine O/control/records. If the watcher exits involuntarily, upstream's deferred single-key deletion may already have erased whatever occupied that key before the relay observes the loss. Report same-key state as possibly deleted/unverified; do not claim preservation or infer route cleanup/retirement from quarantine. Other independent session keys and Serve fields remain outside that daemon deletion. Reprint acquires the existing higher managed-state **T** only while **O** is held, and its status/arm request must trigger a fresh live authority check; ledger or last-known state is not proof.
8. **Reconcile the session key before closing L.** First close the bootstrap gate and stop the public listener, but keep the watcher/session L live while reconciling. The pinned daemon closes a foreground watch by calling `DeleteForegroundSession(sessionID)`, which deletes whatever is currently stored at that key; closing the watch is therefore itself a mutation, not a harmless final step. The R2 cleanup adapter must round-trip the full pinned `ipn.ServeConfig` schema (or a schema-preserving equivalent), so recognized unrelated services, background mappings, sessions and Funnel fields survive; unknown fields/version fail closed. Read the complete Serve view while L is live and inspect the whole `Foreground[sessionID]` value. Only a settled-success registration, or an unresolved registration whose exact submitted route is now visible, may conditionally remove the key—and only when its entire value is exactly this run's single submitted config. Use a fresh non-empty ETag, require a complete acknowledgement, then read again while L is still live and require the key to be absent. A settled-success whose key is already absent may proceed because its POST is settled. A settled 412/no-write may proceed only if the key is absent; if any key content exists, it is a conflict. If the key is changed, expanded, or otherwise not exactly the submitted value, do not POST or intentionally cancel L: retain the owner in `unknown/not-retired` quarantine and make no relay cleanup mutation. The observed same-key value remains untouched only while L stays live. UP-003/UP-004 make clear that a subsequent involuntary watcher exit may still trigger unconditional deletion of that value before the client observes loss; do not claim same-key preservation after that event. Only after absence has been confirmed with L live may the owner deliberately cancel the watch request, close its response body and join the local reader; under the session-key noninterference assumption, the daemon's single-key deletion then finds no same-key route. That ordering does not protect against an intervening accidental same-key repurpose or involuntary loss. This proves only that the client stream is closed. UP-003/UP-009 provide no daemon-side close acknowledgement, completion event, or finite cleanup deadline, so a final GET—even if absent—does not prove the deferred server cleanup has completed. Report separate `route_cleared` and `watcher_close_unverified` states; never convert local cancellation/reader exit into `retired=true`, release O, or let the shell stop the process. Retain the owner/control/recovery record as `unknown/not-retired` unless separately reviewed source evidence supplies a daemon-side close acknowledgement. On definite 412, re-read/recompute while L remains live (at most three conditional route-cleanup attempts within the normal 5-second route budget); after an ambiguous cleanup acknowledgement, re-read before any fresh-ETag retry. Never blindly replay a POST. Preserve unrelated recognized config; never clear globally. The no-malicious-same-UID-writer threat boundary still applies; this sequence does not invent an atomic cross-writer fence absent from the source.

For an `unresolved` registration, an absent effective-view read while L is live is **not** evidence that the POST has settled or that the route is retired. Immediately stop public service and keep pairing disabled, but do not close a still-live watcher, acknowledge `retired=true`, release O, or let the launcher stop the owner. Enter a quarantined state with the process/O/L/control endpoint retained; the control response is explicitly `unknown/not-retired`. If an exact submitted route later appears, conditionally remove that exact entry while L remains live and require the cleanup acknowledgement plus a live-watcher post-write absence read before attempting deliberate local stream cancellation. If the route is changed or expanded under the same ID, make no cleanup write and do not intentionally cancel L; retain L/O/control/records in quarantine. This leaves that observed value untouched only while L remains live: an involuntary watcher exit may still cause upstream to delete it before the relay can react, so same-key preservation is not guaranteed and quarantine does not fence the daemon. Other independent keys/Serve fields remain outside the single-key deletion. Even after a successful route removal, watcher cleanup remains unverified after local cancellation; no timeout, local reader exit, or sequence of absent reads promotes it to `retired=true`. If it remains absent, or the watch/API is lost, keep unknown and require explicit operator recovery. Retaining O is only a local takeover fence, not a Tailscale cleanup guarantee; the route may still appear later. Do not claim raw StateStore bytes were erased when the daemon's effective view filters an inactive entry.

The existing `runServe` currently unconditionally defers `RetireManagedOwner`; R2 must gate that retirement on positively verified cleanup and keep the owner process alive in quarantine rather than returning through that defer. With only the presently sourced APIs, local stream closure has no daemon-side acknowledgement, so the candidate cannot report a positive watcher-retirement result or safely release O; the relay must remain unavailable unless further pinned-source research establishes such an acknowledgement. The launcher retains its run record and does not stop the quarantined process on `unknown`. If a quarantined process is forcibly killed, retained metadata is not a daemon-side fence and does not prove the route absent.

`O` remains the local managed root/lock, **L** is the live Tailscale watcher/session, and **T** remains the existing temporary reprint/state transaction; none substitutes for another. Any private localcontrol readiness field reports a live in-process validation result and is not itself the authority.

### Existing bootstrap/readiness integration gap

Today `runServe` calls `app.NewOwned` before `Server.Run`; `newServer` opens the device store, calls `armBootstrap`, then installs the raw store as the Hub's E2EE auth resolver ([`internal/app/server.go`](../../internal/app/server.go#L269-L282), [`armBootstrap`](../../internal/app/server.go#L338-L347)). `Hub.HandleWebSocket` snapshots that resolver before each handshake ([`internal/transport/ws.go`](../../internal/transport/ws.go#L180-L195)); the handshake calls `ResolveE2EESecret` and later `CompleteE2EEAuth` ([`internal/transport/e2ee.go`](../../internal/transport/e2ee.go#L206-L221), [`internal/transport/e2ee.go`](../../internal/transport/e2ee.go#L305-L313)). The store's `ResolveE2EESecret` refreshes and persists an expired bootstrap invitation when the invitation is the bootstrap ID and there are no credentials ([`internal/deviceauth/resolver.go`](../../internal/deviceauth/resolver.go#L24-L42)). Skipping constructor `EnsureBootstrapInvitation` alone is therefore insufficient. `Server.Run` also marks `s.ready=true` on listener bind and reuses that flag for `/healthz`, `/readyz` and pairing status ([`internal/app/server.go`](../../internal/app/server.go#L1351-L1363), [`pairingControlStatus`/`armBootstrapForControl`](../../internal/app/server.go#L2832-L2872)).

For a validated managed Tailscale run, R2 must use the proposed non-mutating `deviceauth.OpenDeferred` path and must never expose the raw store directly as `Hub`'s resolver. Install a revocable Tailscale-session auth gate around the store in the closed state: while closed, it rejects resolver `ResolveE2EESecret` and `CompleteE2EEAuth` before delegating, including both invitation and credential selectors. This prevents invitation refresh/consumption and credential-completion persistence before route readiness. Closed-gate results are transient, not permanent credential rejection. After live route validation, the owner may protect/create the store directory as needed, persist only the bootstrap invitation for arming, and then open the gate; subsequent credential operations retain their existing behavior and existing credential records are preserved. Never reset/revoke credentials or enable `RearmBootstrap`. The gate synchronizes closure with in-flight operations and closes before public listener retirement on owner loss.

After the live session, exact route and local/TLS health pass, the owner-side arm callback revalidates O/L, persists the invitation, verifies it, then opens the gate and reports pairing-ready only with the durable localcontrol acknowledgement. Split **local service readiness** from **pairing/authority readiness**: local `/healthz` can report the bound backend/inventory, while `localcontrol.Ready` remains false until live owner validation, route/identity/version/TLS/health, persisted arm and gate-open all pass. Startup and reprint callers must use that callback, not an earlier status bit. Keep non-Tailscale startup behavior unchanged.

### Launcher migration and cleanup handoff

The current [`relay/tailscale.sh` path](../../relay/tailscale.sh#L264-L293) starts a separately supervised `tailscale serve` child after the relay reports localcontrol readiness, records its PID/log, monitors it, then stops it and requires global `serve_configured=false`/`funnel_configured=false`. That sequence is incompatible with the proposed `runServe` owner: it would create a second watcher/session after the in-process owner had already registered its exact route. **R2 must remove, not supplement, the external `tailscale serve` child.**

The proposed replacement is a two-phase launcher handoff so the owner lock and run record precede the first route write:

1. Keep CLI `tailscale inspect` strictly read-only for pre-consent identity/version and empty-config checks. Obtain per-run consent; do not invoke a Tailscale Serve CLI command.
2. Start the single supervised relay process. `runServe` acquires O, opens the server in local-ready/pairing-disabled mode, creates its private control socket and reports an in-process `owner_held`/`local_ready` status; it has not opened L or submitted a config write yet.
3. The shell writes the selected transport/origin and non-secret run record only after that O-held status, then sends an authenticated localcontrol `activate` operation. This is the only path that lets `runServe` open L and submit the one exact conditional registration. No caller passes a session ID or `owned=true`.
4. The owner reports `serve_ready` from its live handle and exact route; the shell checks trusted public HTTPS/health, then `arm_bootstrap` asks the same owner to revalidate, persist the invitation and open the gated resolver. Pairing `ready` is reported only after the durable acknowledgement. `setup-link.sh` may use read-only Inspect for node identity but must stop requiring `Inspect.ServeRouteOwned=true`; it stays false by contract and is replaced by the in-process status/reprint proof.
5. Preserve only the supervised relay process tree (`RELAY_PID/JOB/LOG`). Remove the `$TS_BIN serve` invocation and its `SERVE_PID`, `SERVE_JOB`, `SERVE_LOG`, capture/wait/monitor code, session-file Tailscale child PID, child stop/signalling, and global-empty cleanup query. Keep generic `common.sh` process helpers for the relay itself; do not add a CLI Serve fallback.

Before normal relay shutdown, the shell requests an authenticated, idempotent localcontrol `retire` operation bound to run ID/instance. It revokes pairing readiness, closes the bootstrap gate, stops the public listener, and performs exact-route reconciliation/removal while the watcher remains live. Report route cleanup separately from watcher closure. The shell may remove records and signal/reap the relay only after a source-backed positive watcher-retirement acknowledgement and clean owner exit; unrelated routes do not make exact-route cleanup fail and are never deleted. The currently pinned sources expose no such close acknowledgement, so with the present evidence the response remains `unknown/not-retired`, records/O are retained and the relay is not stopped; R2 must not claim normal retirement until further source evidence closes this gap.

If activation/write is unresolved and the owner returns `unknown/not-retired`, the launcher retains the record/logs, returns failure, and **does not signal or kill the still-live owner**; it stays quarantined holding O and, when possible, L/control. Do not roll back selected transport/origin files referenced by that process. If the owner already exited or acknowledgement is lost, do not run the old global-empty test; retain records for explicit recovery. Abnormal death cannot be certified from PID or global config. The record contains only run ID/instance and non-secret diagnostics: never serialize the LocalAPI session ID, watcher handle, or auth material. R2 must gate `RetireManagedOwner` on positive retirement. Neither a retained record nor O prevents an already-submitted remote POST from committing.

## Proposed protocol bounds

These are R2 design targets, not current implementation guarantees: one-shot LocalAPI status/config/version and localcontrol exchanges have a 5-second context deadline and a 1 MiB maximum response; parse one complete UTF-8 JSON value with the existing depth-32, 100001-token ceiling and duplicate/case-conflict rejection. A watch has no fixed lifetime deadline, but its first event must arrive within 5 seconds, each newline-delimited JSON event is capped at 1 MiB and parsed under the same structural limits, and run cancellation closes the stream. Maintain one outstanding LocalAPI operation; monitor at 2-second intervals with one operation at a time. For settled registrations, use a 5-second total retirement budget: exact-session reads no more frequently than every 250 ms and no more than three conditional cleanup writes, each based on a fresh complete config and non-empty ETag while L remains live. A definite 412 or ambiguous cleanup acknowledgement requires a fresh read and exact-state re-evaluation before watch closure; no blind mutation retry is permitted. An unresolved registration gets only a 5-second budget to enter `unknown/not-retired`; elapsed time, absent reads and retained O never settle it. Keep its quarantine/control state until explicit recovery. Health checks are individually bounded to 5 seconds. Diagnostics are capped at 64 KiB, exclude auth tokens/raw session data, and are never used as authority.

A small standard-library-only adapter avoids that module graph only by reimplementing platform credential discovery, local socket selection, authentication, protocol/version checks and conditional writes; it is not the recommended shortcut.

## Alternatives compared

- **Keep unavailable:** preserves the current safe refusal; no feature. Mandatory fallback for every unapproved/unqualified cell.
- **Continue external `tailscale serve` CLI child:** upstream CLI itself owns a watcher and sends conditional config, but its parent receives only process lifetime/output, not a supported cross-process authority handle. A PID, URL or route observed afterward does not identify the watch. Not sufficient for relay pairing/reprint/cleanup. R2 must remove this child from the Tailscale launcher entirely, not run it beside or as a fallback to the in-process owner.
- **Relay-owned pinned LocalAPI watcher (preferred candidate):** can tie watcher, session ID, O and app server to one run and use daemon ETag conflicts. Requires explicit version/distribution/dependency/permission approval, bounded protocol handling, lifecycle integration and per-cell runtime qualification. API is unstable across releases.
- **Newer upstream interface:** no independently sourced/documented newer API contract was established in this R1 research. Do not claim a newer interface exists or is safer without a separate pinned-source review.
- **Custom patched Tailscale CLI:** could expose a parent contract but adds a maintained fork, signing/packaging/updating burden and still needs tests. Not preferred absent owner funding/scope.

## Trust and threat model

The cooperating-writer boundary is precise: each writer reserves and modifies only its own ephemeral watcher-session key. The relay's selective registration/removal may modify only its `Foreground[sessionID]`; other routes, background fields and independent session IDs remain untouched by those writes and by the sourced daemon's single-key `DeleteForegroundSession`. Any writer that repurposes or replaces this run's ephemeral key violates this session-key noninterference assumption, even if the change is accidental. If a changed/expanded same-key value is detected while L remains live, fail closed: issue no cleanup write, do not intentionally cancel L, and retain O/control/records in quarantine. This leaves the currently observed key untouched only while L remains live. UP-003/UP-004 establish that any later watcher exit, including involuntary loss, may delete whatever then occupies that key before the relay can observe the loss. Neither quarantine nor O fences that daemon action; **same-key preservation after involuntary watcher loss is outside the guarantee**. Unconditional protection would require a different daemon primitive or a maintained fork, outside R1 and not approved.

The design also does not defend against a malicious process running as the relay's UID or a process with root/operator/Mac LocalAPI authority. Such a process can omit `If-Match`, create/cancel watches, replace keys or change other local Tailscale state. The LocalAPI write permission is broad, not Serve-only; the relay cannot reliably distinguish such an actor. This shares DR-2's same-UID filesystem/TOCTOU boundary: neither O/T nor a private socket is a defense. A stronger adversarial guarantee requires a separately approved privilege broker/OS boundary or the feature remaining unavailable.

The watcher-plus-session-ID is an in-memory run handle, not a secret bearer token. LocalAPI transport tokens, macOS same-user-proof material and any authentication material are sensitive: keep them only in the upstream transport/memory, never in logs, argv, environment, session files or QR output. No product support is claimed for the malicious same-UID/root/operator threat model.
